## Executive summary

This audit assesses the implementation at commit `7132b33` (the audited code baseline). [requirements.md](requirements.md) governs intended behavior; [specification.md](specification.md) supplies the 82 requirements and their acceptance criteria. [verification.md](verification.md) describes proposed demonstrations, not executed evidence. This audit does not turn current implementation policy into requirements.

The implementation is a substantial, locally tested workflow prototype with durable task/session records, revision checks, project mutation queues, attachment materialization, exact-content quality evidence, conservative Git checks, and several restart-reconciliation paths. It is **not yet an implementation of the agreed architecture**. Important happy paths exist, but their composition still depends on quality approval, operator recovery, and multiple independently persisted records. Local tests sometimes deliberately assert behavior that the requirements prohibit.

The most consequential findings are:

1. **Advisory steps are not consistently advisory.** Initial validation exhaustion and some unavailable/negative implementation reviews can produce draft PRs, but plan verification is mandatory, CI repair requires passing review, feedback publication requires passing local checks, and maintenance requires passing checks and review. See [F1](#f1-quality-policy-and-publication) and [F2](#f2-remediation-bounds-and-ci-episodes).
2. **Human control and additive Git history have explicit conflicting implementations.** `autoMerge: true` can invoke a GitHub merge; published-PR maintenance rebases and uses `--force-with-lease`. A lease reduces overwrite risk but is still a force-push and rewrites published history. See [F3](#f3-human-pr-outcomes-and-terminal-races) and [F4](#f4-git-isolation-history-cleanup-and-clean-retries).
3. **Preservation is stronger than automatic recovery.** Many errors safely retain work, but enter an absorbing `attention-required` state or require a Trello move/restart rather than automatically resume after dependency recovery. Plain lock files can survive a crash. Session replacement/context reconstruction is absent. See [F5](#f5-persistence-recovery-and-operation-liveness).
4. **Cross-service consistency remains incomplete.** PR lookup, trusted commits, and reply markers provide useful safeguards, but there is no uniform durable intent/outcome protocol for PR creation, Trello comments, card transitions, refinement updates, or email. A late accepted write after a negative read is not generally reconciled safely. See [F6](#f6-external-mutations-and-partial-publication) and [F7](#f7-refinement-and-setup).
5. **Ownership is scoped to configured storage and aliases, not canonical integrations.** Queue locks cannot coordinate separately configured roots or local/container namespaces. Active integration identity and paths are not durably pinned. Optional global AI capacity and fair cross-project slot allocation are absent. See [F8](#f8-configuration-ownership-and-scheduling).
6. **Verification is broad but predominantly mocked.** Real local Git tests exercise selected operations; no inspected record establishes a realistic complete Trello/GitHub/OpenCode lifecycle or local/container parity. See [Verification gaps](#verification-gaps).

Status totals are recorded under [Coverage totals](#coverage-totals). A `Partial` status is not a readiness claim; an explicit conflict takes precedence over partial support. The rewrite must coordinate workflow policy, ownership, external-operation recovery, and evidence reporting rather than repair each symptom independently.

## Scope, method, and evidence conventions

- Inspected production entrypoints, the complete requirement/acceptance-criterion inventory, workflow dispatch and recovery, service clients, persistent schemas/stores, prompts, configuration schema/examples, test suites, CI, and operator documentation. Private `.env`, local production configuration, and runtime task data were not needed as audit inputs.
- Evidence is repository-local unless explicitly stated. Paths are relative to the repository root. Function/class names and line ranges identify the audited revision; later edits may shift lines. Test references identify relevant suites or named cases, not an assertion that every criterion is tested.
- **AC1**, **AC2**, etc. refer to the acceptance-criterion bullets in each specification section, in order. Every criterion is evaluated in the matrix. Shared findings explain overlapping gaps once, with production and test references.
- **Implemented:** sufficient implementation evidence supports every criterion. **Partial:** some criteria are supported, with important gaps. **Missing:** the required capability is absent. **Contradictory:** an implemented policy conflicts with an explicit criterion. **Unverified:** insufficient evidence permits a reliable overall conclusion.
- Prompt instructions establish supplied guidance, not actual agent compliance, semantic task quality, or filesystem confinement. A mock accepting a move does not establish that Trello reached the destination. A real local Git test with a mocked GitHub object establishes Git behavior, not live API compatibility.
- Missing mechanisms below are conclusions about the inspected source/configuration/test inventory, not claims about undocumented operator scripts or a deployed installation. Suspected race consequences are identified as risks, not reproduced production incidents.

## Detailed findings

### F1. Quality policy and publication

**Affected:** REQ-PR-001–004, REQ-IMP-003, REQ-VAL-001–005, REQ-HR-002/004/005, REQ-CI-002, REQ-MNT-003, REQ-CTX-002.

**Current behavior and evidence:**

- `src/orchestrator/run-task-session-workflow.ts:2814–2860` runs independent plan verification and throws when its verdict is not `pass`. `runTaskSessionImplementation` in `src/task-session/run-task-session-implementation.ts:201–244` independently requires configured validation and a passing verified plan. `src/opencode/build-task-session-implementation-prompt.ts` and `task-session-prompt-guidance.ts` constrain implementation to approved requirements. `tests/run-task-session-implementation.test.ts` explicitly tests refusal of missing validation and unverified plans; `tests/task-session-prompt-guidance.test.ts` tests keeping implementation constrained to the verified plan.
- Initial delivery is more permissive: `publishWithoutReview` in `run-task-session-workflow.ts:3079–3286` publishes exhausted-validation or unavailable-review work, and its final review path can publish exhausted findings. `decideHumanReviewPublication` in `src/task-session/verified-publication-decision.ts:100–121` tolerates negative/missing evidence subject to source-staleness checks. `tests/verified-publication-decision.test.ts` includes “allows a human-review PR despite missing or failed quality evidence”; `tests/publish-task-session-card.test.ts` covers content-bound publication. These helpers do not establish that all callers reach publication.
- Other callers use a different rule: `decideValidatedHumanReviewPublication` in that same module requires passing local checks. Feedback uses it at `src/orchestrator/run-task-session-feedback-cycle.ts:926–929,1053–1056,1115–1116`. CI repair explicitly throws for negative review at `run-task-session-workflow.ts:1255–1258` and checks publication gates at `1398–1399`. `verifyPreparedPrMaintenance` in `src/task-session/verify-prepared-pr-maintenance.ts:150–195` rejects failed validation/coverage, any non-pass review, unsatisfied requirement, or blocking finding. `tests/verify-prepared-pr-maintenance.test.ts` asserts these gates.
- `src/config/config.ts:329–335` rejects missing validation despite its optional property declaration. `runTaskSessionCoverage` in `src/task-session/run-task-session-coverage.ts` returns `null` when unconfigured. `runTaskSessionValidation` in `src/task-session/run-task-session-validation.ts:144–182` runs the actual command and records status, exit, timing, diagnostics, and content identity, including timeout/abort. There is no complete explicit skipped/uncertain quality-outcome ledger across all stages.
- `src/orchestrator/publish-card.ts:676–688,774–810` selects/enforces draft based on exhausted review or `reviewResult !== "Passed"`. It does not independently evaluate all unresolved human requests or absent commands. No draft-to-ready client operation was found. Passing or failing an AI verdict is not the same as a deterministic record of material unresolved issues.

**Required behavior and difference:** all listed quality activities are optional advice or bounded improvement opportunities, never implementation/publication approval. Initial-delivery exceptions do not satisfy the same requirement in CI, human feedback, recovery, or maintenance. Quality evidence must determine honest reporting/readiness without substituting reviewer approval for engineering judgment. The rewrite needs one consistent distinction between publication safety, primary execution failure, optional advice, and known quality concerns. Current positive-review gates are confirmed contradictions, not merely missing tests.

### F2. Remediation bounds and CI episodes

**Affected:** REQ-PR-002, REQ-VAL-003/004, REQ-HR-005, REQ-CI-001/002, REQ-WF-002/003.

`MAX_VALIDATION_REPAIR_ATTEMPTS` in `src/task-session/run-task-session-validation-repairs.ts` and `MAX_CI_REPAIR_ATTEMPTS` in `src/task-session/run-task-session-ci-repairs.ts` are both fixed at two. Only AI review's `project.opencode.remediation.maxPasses` is configurable. `task-execution-record.ts:313–328,475–489` also embeds the two-attempt rule into schema validation. Separate counters therefore exist without the required separately configurable policies.

`runTaskSessionValidationWithRepairs:367–434` increments before dispatch and stops at its durable bound, but does not compare before/after source identity to stop a successful no-op repair. `runTaskSessionReviewWithRepairs` in `src/task-session/run-task-session-review-repairs.ts:160–249` likewise repeats review after successful repair and quality rerun. It checks unchanged source only when repair **throws**. A maximum becomes effectively mandatory when the reviewer remains negative. `tests/run-task-session-validation-repairs.test.ts` and `tests/run-task-session-review-repairs.test.ts` exercise bounds/stale evidence, not a general agent-declined-advice finish contract.

CI has a specific budget risk: `runTaskSessionCiRepairs:94–99` constructs `cycleId` from operation key **and starting head SHA**, resetting the counter when it differs. Within one invocation, new heads retain the local cycle; after a return for pending CI and a later invocation on the new self-generated head, the calculated cycle differs. Poll dispatch also keys repair events by head (`run-task-session-workflow.ts:1068–1076`). This is a code-supported reset risk; it was not reproduced against live CI. The required episode must instead survive its own commits/reruns and be renewed only by a verified new initiating event. A same-head no-change repair currently throws (`run-task-session-ci-repairs.ts:150–156`) rather than ending improvement normally.

`evaluateCiChecks` in `src/github/evaluate-ci-checks.ts`, `establishCiCheckExpectations` in `ci-check-expectations.ts`, and `src/github/ci-workflow-contract.ts` conservatively distinguish missing/pending/uncertain expectations and exact heads. However, `run-task-session-workflow.ts:1062–1066` continues on waiting/uncertain without any persisted first-observed time or wait bound. `tests/task-session-dispatch.test.ts` explicitly exercises waiting for delayed registration and mixed pending/failing checks without repair attempts; it does not demonstrate eventual bounded exit. `tests/run-task-session-ci-repairs.test.ts` covers two-attempt repair and wait results, not an episode that remains exhausted across later head-keyed invocations and routine maintenance.

**Rewrite implication:** repair count, content identity, and initiating-event identity cannot be interchangeable. They need coordinated semantics with early/no-op completion, optional advice, durable wait bounds, and draft reporting; merely adding another numeric setting will not address the lifecycle resets.

### F3. Human PR outcomes and terminal races

**Affected:** REQ-PR-008, REQ-TR-001/002, REQ-HR-005/006, REQ-GIT-004/005, REQ-SCH-001, REQ-CTX-004.

`src/config/config.ts:229–236` accepts `autoMerge`. `runTaskSessionWorkflow` invokes `mergeTaskSessionPullRequest` on passing readiness both during review observation and after initial publication (`run-task-session-workflow.ts:3923–3993`); `src/orchestrator/merge-task-session-pull-request.ts` calls the GitHub merge path. `tests/task-session-auto-merge-lifecycle.test.ts` explicitly verifies automatic merging after delayed checks pass. This directly contradicts “never automatically merge,” even though default configuration disables it. `tests/publish-card.test.ts` saying publication itself never merges does not prove the coordinator never merges.

Terminal handling has real safeguards: `completeMergedTaskSession` checks merged time, repository/base/head, and recorded-head continuity; `verifyMergedTaskPrHeadContinuity` is in `src/orchestrator/verify-merged-task-pr-head-continuity.ts`. `completeMergedTaskSessionPullRequest` and `returnClosedTaskSessionPullRequestToBacklog` in `src/orchestrator/reconcile-terminal-task-session-pr.ts` implement the correct normal destinations, with queue replay and deletion-race handling. `tests/task-session-terminal-pr.test.ts` covers deferring merged cleanup for a live queue owner and recovering an orphan claim. Destination and comment verification limitations are in F6.

The worker awaits the entire `pollProject` call. There is no concurrent per-project terminal observer that aborts only the current task operation when a human merges/closes while OpenCode is editing. Maintenance checks PR identity before preparation/push and reconciles publication intent (`src/orchestrator/maintain-outdated-pr.ts`, `src/task-session/pr-maintenance-store.ts`); that is valuable but not lifecycle-wide cancellation. In ordinary publication, `publishCard` may push at lines 617–649 before finding the current PR at 658–673. Existing-PR identity is checked earlier too, but that read does not prevent a human closing/deleting the branch after it. A late ordinary push can therefore recreate a removed branch before a subsequent read rejects the outcome. This is a confirmed ordering exposure, not evidence that it occurred in production.

`src/orchestrator/reconcile-unobserved-terminal-pr.ts` also permits retiring certain terminal queue events when the card is no longer observed in the expected review list, without moving/recreating the missing card or deleting its worktree. That conservatively avoids destructive guessing, but is not proof of a verified terminal Trello outcome. Manual relocation, disappearance, and a confirmed terminal workflow result need distinct ownership semantics.

**Required difference:** a verified human terminal event supersedes all queued/running mutations, including stale completions. Cancellation, unshipped-work preservation, late write reconciliation, and terminal Trello release must compose across every correction route. The existence of a terminal queue event alone does not prove this race is solved.

### F4. Git isolation, history, cleanup, and clean retries

- `prepareWorktree` in `src/git/prepare-worktree.ts:194–258` creates `agent/<card-id>` under the configured worktree root from the fetched default branch. `assertOwnedTaskWorktreePath` in `src/task-session/run-task-session-implementation.ts` rejects unsafe/overlapping/symlinked locations, and execution checks actual branch. `tests/prepare-worktree.test.ts` and `tests/run-task-session-implementation.test.ts` test these guards. The validation-exhausted fallback at `run-task-session-workflow.ts:3230–3233` uses `chore(task): implement Trello card <id>`, not a descriptive generated task summary.
- Ordinary `publishCard` refuses non-fast-forward publication (`617–647`), but maintenance deliberately takes another path: `preparePublishedPrRebase` in `src/task-session/prepare-published-pr-rebase.ts` verifies an already-published task, creates a backup ref, and rebases it; `maintainOutdatedPr` in `src/orchestrator/maintain-outdated-pr.ts:398–463` verifies the remote and calls `GitClient.pushWithLease`. `src/git/git-client.ts:326–355` emits `--force-with-lease=refs/heads/...`. `tests/prepare-published-pr-rebase.test.ts` uses real Git, and `tests/pr-maintenance-publication.integration.test.ts` spies on the leased push against a local bare remote. **Required difference:** preservation and retryability must coexist. Attempt-specific artifacts/provenance, publication history, safe terminal cleanup, and fresh manual retry must be redesigned together; deleting retained records or dirty work to unblock the card would violate preservation requirements.

### F5. Persistence, recovery, and operation liveness

**Affected:** REQ-WF-002/003, REQ-PR-003/006, REQ-REC-001–006, REQ-CFG-005, REQ-TR-003, REQ-IMP-004/005, REQ-CTX-004.

`TaskExecutionStore` (`src/task-session/task-execution-store.ts`) validates strict versioned records, fsyncs temporary content, uses atomic replacement, and checks revisions. `TaskMutationQueue` (`src/task-session/task-mutation-queue.ts`) retains one active/failed mutation owner with token/PID checks. `TaskPlanStore`, `FeedbackLedgerStore`, `PrMaintenanceStore`, trusted/pending/rejected commit files, prepared-conflict handoffs, reconciliation blocks, and mutation-block records each add evidence for particular operations. `transitionTaskExecutionRecord` (`task-execution-transition.ts`) provides allowed events with owner/phase checks; the coordinator also makes direct phase/record updates. These are meaningful foundations, not a single transaction across stores or external effects.

`reconcileTaskSession` in `src/task-session/reconcile-task-session.ts` reads an authoritative snapshot and verifies worktree/branch/head/session/Trello/PR/CI state. But `attention-required` returns immediately at lines 123–129; failed snapshot reads, inaccessible sessions, unexpected lists, or active/changed setup can convert recoverable conditions to that phase. Returning a manually moved card to its expected list does not generally restore the prior phase. `tests/reconcile-task-session.test.ts` and `tests/task-session-dispatch.test.ts` test conservative escalation; the latter explicitly tests parking a legacy attention task without mutation. This avoids unsafe continuation but does not satisfy automatic bounded reconciliation or a useful service-wait state.

`runProjectWorker` in `src/orchestrator/run-orchestrator.ts` uses bounded transient attempts/backoff, persists selected blocks, and suppresses selected repeated alerts. After exhaustion it waits for `card-moved-to-ready` or `worker-restart` (`713–823`); `hasReconciliationRecovery` checks those operator signals, not recovery of the dependency itself. Malformed blocks are retained indefinitely. `tests/run-orchestrator.test.ts`, `tests/reconciliation-block-storage.test.ts`, and `tests/retry-backoff.test.ts` cover these policies. Thus preserved outage state is real, but automatic resumption after an outage is not generally implemented.

Plain file locks have a separate crash boundary. `TaskExecutionStore.withLock:344–368` and `FeedbackLedgerStore.withLock:250–273` create exclusive `.lock` files and unlink only in `finally`. Killing the process before `finally` leaves a lock with no durable owner/lease metadata to reconcile. `cleanupPersistedStateTemporaryFiles` in `src/orchestrator/persisted-state-temporary-files.ts` handles recognized atomic-write temporaries, not these locks. Queue PID recovery does not recover storage locks. Safe writes therefore coexist with a stale-lock liveness risk.

`runWithPrimaryTaskSession` in `src/task-session/primary-task-session.ts` persists session-creation intent, binds a returned ID, reuses it, and refuses ambiguous replacement. `inspectPrimaryOpenCodeSession` in `src/opencode/inspect-primary-session.ts` checks listed session identity/directory. There is no bounded reconnect/reconstructed replacement path when a bound session is truly gone. `tests/primary-task-session.test.ts` and `tests/inspect-primary-session.test.ts` exercise mock outputs, not a real restarted OpenCode process/session store. Source/session safety uncertainty must not be bypassed, but indefinite escalation is not the required recovery implementation.

`runTaskSessionImplementation:273–342` immediately records terminal pending failure on a nonzero primary result; thrown errors become attention. The coordinator confirms the Failed list before release (`run-task-session-workflow.ts:3998–4049`), which is a useful exception to weaker move verification elsewhere. It does not first exhaust a bounded primary recovery policy, and this handler does not invoke `failCard` to supply the required explanatory comment/failure email. Quality-step execution failures and primary failures still have inconsistent handling across callers.

`RuntimeLifecycle` in `src/runtime/runtime-lifecycle.ts` converts signals/fatal failures to coordinated abort; OpenCode and `CommandRunner` send process-group TERM then KILL. `tests/runtime-lifecycle.test.ts`, `tests/command-runner.test.ts`, and `tests/opencode-streaming.test.ts` cover interruption and output capture. Git uses fixed-timeout `execFile`; gh uses fixed-timeout `spawn` with direct-child TERM/KILL. Neither receives the workflow AbortSignal. `ensureRepository` invokes clone without a command timeout. There is no task-wide deadline, which matches the requirement, but no general meaningful-progress/stall monitor either. Strict version-1 parsing preserves unsupported records by rejecting them (`tests/task-execution-record.test.ts`); selected legacy compatibility branches are not a general safe migration/upgrade contract.

**Required difference:** recovery must distinguish recoverable dependency wait, actual unrecoverable primary operation, interrupted optional advice, unknown ownership, and terminal synchronization. Preserve evidence in all cases, but give each a deterministic recheck/recovery/finalization path. A single attention phase currently conflates these categories.

### F6. External mutations and partial publication

**Affected:** REQ-WF-001, REQ-PR-004–006, REQ-TR-001/002, REQ-REF-004/005, REQ-REC-001/003, REQ-NOT-002.

`TrelloClient` in `src/trello/trello-client.ts:586–648,683–711` parses card responses for moves/content writes, while label removal/addition has no final card readback. Callers commonly await `moveCard` and log completion without asserting the returned `idList` or independently reading authoritative destination state. Examples are `publishCard:835–852`, terminal handlers in `reconcile-terminal-task-session-pr.ts`, and `finalizeRefinement`. An acknowledged, parsed response is evidence of an operation, but a schema-valid wrong destination is not sufficient verification of the intended transition. Mocked call-order tests do not close this gap.

Initial publication has a significant persistence window. `publishCard` pushes/locates or creates a PR, then moves Trello, sends email, and posts a comment. `runTaskSessionWorkflow` persists the PR into its task record only after `publishCard` returns and a separate PR/head lookup succeeds (`3240–3266` and the normal publication path). If the PR exists but Trello move fails, `PublishedCardStateError` carries a message, not a durably saved PR identity/creation intent. `reconcileTaskSession:215–234` explicitly escalates when a PR is discovered without persisted identity rather than automatically associating it. This blocks a new task safely but does not accomplish the required automatic reconciliation.

PR and remote-head lookup reduce duplicate effects in ordinary retries (`tests/publish-card.test.ts`: “reuses an existing pull request instead of creating another one,” “does not push again when the remote branch already has the commit”). They do not cover a timed-out create accepted after the next negative lookup. No persisted initial creation intent or controlled late-acceptance discovery state was found.

Reply publication is stronger but incomplete. `publishVerifiedFeedbackReplies` in `src/task-session/publish-verified-feedback-replies.ts:144–187` writes a stable marker and sending/outcome-unknown state. However, a later reconciliation result `absent` falls through to send again, regardless of earlier uncertain acceptance. `run-task-session-feedback-cycle.ts:350–384` maps a missing marker to absent. A negative read while the original write is still in flight is not proof of nonacceptance. `tests/publish-verified-feedback-replies.test.ts` covers reconciliation/uncertainty, but not a late acceptance after a negative lookup with independent service-effect counting.

Trello comments are even less durable: `publishCard:896–904`, closed-PR comment handling (`reconcile-terminal-task-session-pr.ts:224–235`), and `failCard:124–154` log comment errors and continue/throw the original error without a pending comment intent. A closure comment can be permanently lost after the card has already moved, because an already-Backlog replay skips it. Refinement's completion comment is also a separate effect. No general discoverable operation marker/deduplication policy exists for these writes.

**Required difference:** external mutations need an explicit distinction between safely repeatable state setting, discoverable resource creation, and potentially non-discoverable/non-idempotent writes. Persist intent before dispatch, preserve ambiguous acceptance, and retain project ownership until the actual outcome is reconciled. This cannot promise unconditional exactly-once effects; unresolved uncertainty must remain observable instead of authorizing blind resend or false completion.

**Required difference:** output validation, repository read-only proof, card intent preservation, human-edit conflict reconciliation, setup attribution, and verified completion are separate obligations. Startup `gh` compatibility checks (`src/github/github-cli-compatibility.ts`, `GitHubClient.validateCliCompatibility`) validate version, help options, and a repository-scoped field probe. `runStartup` then bootstraps repositories sequentially before workers. A failure in this common phase aborts healthy projects too. Git is exercised through repository validity, but there is no equivalent pre-task Git/OpenCode version/capability check. Merge capabilities are checked even for projects without enabled auto-merge. `tests/github-cli-compatibility.test.ts` and `tests/run-startup.test.ts` prove those narrower checks.

`main` loads config once (`src/main.ts:42`) and passes the resulting object down. No live reload exists. Persisted task identity in `task-execution-record.ts` consists of alias/card/branch/session/operation/PR, not the original Trello board/list mapping, repository identity/paths, or context-root pin. `TaskExecutionStore` and `TaskMutationQueue` derive locations from the **current** root and alias. A restart with a removed/renamed project or relocated root does not have a common durable ownership registry from which to reject incompatible configuration. Unknown-version rejection protects a file only if it is found.

Queue protection is useful but local to a file namespace. `TaskMutationQueue` keys `<contextRoot>/task-mutation-queues/<project-id>.json`, uses transient `.lock` updates and owner token/PID, and checks `process.kill(pid, 0)` for recovery. `runOrchestrator` (`src/orchestrator/run-orchestrator.ts:1023–1049`) starts independent workers with `Promise.all`. Human Review does not actively consume an AI process between polls, but that is not a global slot policy.

Fresh Ready discovery filters start dates and workflow type, queues in observed list order (`run-task-session-workflow.ts:2465–2469,2492–2606`), and rereads eligibility before claiming. `tests/card-start-eligibility.test.ts` includes exact start boundaries; `tests/task-session-refinement-scheduling.test.ts` tests mixed-type ordering. The coordinator processes CI before maintenance and then feedback; human-requested changes do not have the required default priority.

Polling uses one required global `pollIntervalSeconds`, without a schema default. Backoff is controlled by `src/orchestrator/retry-backoff.ts`. Each worker awaits all task execution, avoiding same-worker overlap but suspending fresh feedback/terminal observation during long agent runs. Maintenance is dispatched only when `maintenance.enabled === true`, with missing plans skipped (`run-task-session-workflow.ts:1773–1797`); `tests/task-session-maintenance-dispatch.test.ts` explicitly verifies omission disables it.

OpenCode stage config requires model and variant for five stages (`config.ts:154–172`); planning uses implementation settings, and independent plan verification uses review settings. `buildOpenCodeArguments` in `src/opencode/opencode-client.ts:84–111` always emits both flags. Unavailable explicit selections are not silently substituted, but absent selection cannot defer to OpenCode defaults. `tests/opencode-client.test.ts` and `tests/config.test.ts` verify the existing mandatory contract.

**Required difference:** canonical ownership, active configuration pins, fresh attempt scheduling, optional capacity, event priorities, and startup dependency checks must agree on project identity and operation boundaries. Same-file mutual exclusion is not a substitute for this coordination contract.

**Affected:** REQ-LOG-001–003, REQ-SEC-001–003, REQ-CFG-005, REQ-CTX-003.

`Logger` in `src/logging/logger.ts` writes timestamped scoped text events to cwd-based daily files. `src/logging/session-log.ts`, `OpenCodeClient`, and `CommandRunner` capture process streams separately, with incremental known-secret redaction. ## Cross-cutting architectural observations

### State ownership and transition authority

Task phase, mutation ownership, plan verification, trusted commit, maintenance intent, feedback disposition/reply, reconciliation block, Trello list, and GitHub PR head are distributed across separately written files/services (F5–F6). Several stores independently implement path safety, version validation, locking, revision updates, and atomic writes. This is useful defense in depth, but there is no single recoverable ownership transaction linking them. The coordinator's direct record updates coexist with `transitionTaskExecutionRecord`; phase alone cannot identify the outstanding external obligation.

The task-session coordinator is over 4,000 lines at this revision. Quality-evidence persistence and review/validation/publication orchestration are repeated in its initial/CI paths, `run-task-session-feedback-cycle.ts`, and maintenance verification. Their different gates (F1) show actual policy drift across duplicated responsibilities, not merely a stylistic size concern. Persisted external-operation identity needs to be authoritative enough that recovery need not infer ownership from card location, a branch naming convention, or an error message.

### Concurrency and workflow coordination

One awaited project worker and a same-root mutation queue provide practical serialization, but do not provide canonical cross-instance ownership, cross-project capacity fairness, or ongoing observation of human events during execution (F3, F8). A branch mutation queue and a durable active-task lease are different concepts: an idle open PR still owns the project, even when no mutation is active. Likewise terminal reconciliation must override queued work without discarding in-flight evidence. Current procedural ordering is not the required priority policy.

### Recovery and external-service consistency

The implementation favors preserving uncertain work, which is appropriate. Its weakness is that preservation frequently becomes an operator-only terminal parking state (F5). Waiting must retain a resumable phase/intent, distinguish dependency recovery from deliberate fresh retry, and carry a controlled recheck condition. Storage-lock recovery, external late acceptance, and independent store writes must be considered together. Automatically removing unknown locks or resending uncertain writes would weaken safety rather than solve liveness.

### AI sessions and engineering judgment

Primary session continuity is concretely implemented; replacement-context recovery is not (F5). Mandatory approved plans/review verdicts and explicit all-requirement maintenance approval move engineering judgment into orchestration gates (F1). Deterministic orchestration should own attempts, safety, evidence, and publication mechanics, while the agent decides whether advice warrants changes. Session accessibility, advisory reviewer availability, and primary execution recoverability cannot share one undifferentiated failure rule.

### Git safety and diagnostic preservation

Normal path/cwd checks, dirty-tree refusal, trusted commits, and backup refs are valuable. They coexist with contradictory published rebases/force-with-lease and incomplete proof of local work preservation before cleanup (F4). Attempt identity must connect branch/worktree provenance, published commit history, preserved unshipped changes, and fresh retry without reusing unfinished code. Logs and attachments are also task evidence: deleting completed session logs or expiring a waiting active task's data weakens recovery even if Git itself remains intact (F12).

### Public reporting and internal evidence

Quality results, PR draft state, description, Trello transition/comment, and notification are not one atomic success (F6, F10–F11). A successful PR create with failed Trello synchronization remains published work with pending obligations. A negative review is not a primary crash; a missing check is not a pass; a pre-send notification claim is not delivery. The rewrite must retain these distinctions in durable evidence and user-facing summaries without making advisory reporting an approval gate.

## Verification gaps

### Existing tested behavior

The relevant suites named in F1–F13 cover strict parsing, ownership mismatches, same-root queue contention/recovery, source snapshots, attachment staging/rollback, command timeout/abort/output capture, scoped authentication, bounded local repairs, selected PR discovery, terminal cleanup, and mocked production dispatch. ## Rewrite implications

These are dependency constraints for later design decisions, **not a rewrite implementation plan or task backlog**:

- **Workflow policy and evidence types are coupled.** Advisory outcomes, meaningful completed primary work, genuine primary crashes, safe publication, and draft readiness need compatible semantics across all callers. Changing one publication helper cannot remove gates embedded in schemas, prompts, correction callbacks, and recovery.
- **Ownership, configuration, and attempt identity are coupled.** Canonical host-visible project ownership, pinned integrations/storage, active open-PR occupancy, and clean deliberate retries must agree before cleanup or resumption can safely release anything.
- **Persistence and external operation reconciliation are coupled.** Durable intent, correlation, accepted/unknown outcomes, repeated state setting, non-idempotent writes, and schema compatibility must cover all services. Recovery cannot reconstruct these distinctions reliably from the last phase and current list alone.
- **Scheduling and terminal cancellation are coupled.** Observation of new human requests, CI, maintenance, and terminal events needs durable coordination and safe mutation boundaries while preserving in-flight effects. Optional global capacity must count actual AI execution rather than active tasks awaiting humans.
- **Git history and recovery are coupled.** Additive maintenance, provenance-aware cleanup, preserved unshipped work, and fresh attempts affect trusted commits, publication checkpoints, session context, and terminal reconciliation together.
- **Refinement and setup need explicit effect boundaries.** Repository read-only evidence, setup-produced tracked changes, original/intended/human card content, validation correction, and completion/restoration must remain attributable and recoverable without pretending Trello provides atomic conditional updates.
- **Context, sessions, diagnostics, and public summaries are coupled.** Safely reconstructing primary context requires retained task/plan/attachment/change/feedback evidence. That evidence must survive retention and upgrades while secret inputs/outputs remain controlled. PR descriptions, draft state, comments, and emails should report the same observed facts without claiming advice was approval or notification intent was delivery.
- **Verification must follow observable requirements.** Reuse valuable existing deterministic/local-Git fixtures, but distinguish them from realistic lifecycle evidence and replace conflicting test oracles deliberately. The 82-row matrix and existing verification scenarios provide review inputs for that work after this audit is reviewed.
