# Phase readiness and decision register

Use with [phase execution](phase-execution.md). These are explicit prerequisites,
not automatic evidence that engineering checks passed. The user has approved the
four [P6 decisions](p6-decisions.md): genuine-failure accounting, semantic rubric,
upgrade cohort and bounded isolated live verification. Do not ask for these approvals
again; distinguish approved policy/permission from pending executable proof/resources.
Readiness work is actionable local work; an `OPEN` row does not justify returning
without attempting its stated investigation. Record outcomes in the launched phase
manifest, including decision owner, exact evidence and affected task IDs.

## Resolution rules

1. Technical choices within settled requirements are engineering work. Ask the user
   only when a real product/support/authorization choice is needed, with a concrete
   recommendation and consequence; do not ask for approval of every small task.
2. Open decisions block only dependent acceptance. Progress on unrelated ready
   tasks and fixture/parser work continues. Record what that work cannot prove.
3. For required realistic evidence, obtain resources or an explicit user decision
   defining a separate implementation checkpoint. Never silently defer the required
   level or call that checkpoint fully qualified.
4. A blocked row names what was attempted, observed limitation, smallest unblock
   action and owner. “Test not written,” “helper missing,” and “reviewer cannot run
   Bash” are not external product blockers.
5. No entry here changes the settled no-merge/no-force-push/preservation/advisory
   policy. Record approved decisions by reference in canonical A2/A5 notes and the
   manifest; do not maintain competing numeric-policy copies.
